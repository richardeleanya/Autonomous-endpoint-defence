## 1. Integration flow

- Detection (P1.3/P1.4) emits observations -> case graph (P1.5) groups into cases -> action proposer (P1.4/P2.4) creates signed proposal -> policy engine (P2.1) decides -> containment controller (P2 later) acts -> ledger (P2.3) records proposal, decision, action.
- In P2.5, containment is wired but enforcement may be limited to T1 actions under offline profile; T2+ requires P2 enforcement path and G2 validation.

---

## 2. Packaging

- **Installers:** MSI (Windows), deb (Ubuntu/Debian), rpm (RHEL family).
- **Signed artefacts:** All installers signed by release-signing key (P0.3).
- **Observe-only default:** New installs start in observe-only mode; mode change requires signed policy and is logged.
- **Upgrade/uninstall:** Clean upgrade and uninstall tested (no leftover state).

---

## 3. Offline scenarios

| Scenario | Expected behaviour |
|---|---|
| No network at all | Local detection + Tier-1 actions only; T2+ denied; ledger buffered |
| Policy expiry | Fail-closed for T2+ (R11); T0/T1 continue |
| Clock disagreement | Token/action rejected on skew; fail-closed T2+ |
| Restart mid-incident | Case graph and ledger recovered from store; incident resumes |

---

## 4. G2 test subset (lab execution)

- Run G2 scenarios in lab; collect evidence artefacts (ledger exports, decision logs, harness transcripts).
- Offline profile never exceeds T1 (verified).

---

## 5. Operational behaviour and known limits

- Observe-only default; no actions without explicit signed mode change.
- Known limits: containment limited to T1 in offline profile; T2+ requires policy approval and online corroboration.
- No claims beyond measured G2 results.
